## 재개 범위

기존 3문서 structured/none 답변 검증은 완료됐지만 동일 100문서에서의 후보 검증은 남아 있다.
다음 후보는 structured/none이다. 사업명은 기존대로 메타데이터에 유지하고, 임베딩 입력에는 원문만 사용해 청킹 효과를 비교한다.
기본 fixed/none과 기존 baseline은 유지한다. project_blend의 유료 추가 검증은 이번 제안에 포함하지 않는다.

## 비용 없는 확인

- 원래 100문서, smoke 6문항, sample 14문항의 해시가 기존 baseline 평가와 일치한다.
- 현재 코드의 fixed 10,218청크와 structured 11,844청크는 기존 각 전략의 저장 청크와 정확히 일치한다.
- 100문서 모두 사업명 메타데이터가 있으며 모든 청크에 원래 값이 전달된다. 이는 CSV 매핑 내용 자체의 의미적 정확성을 검증한 것은 아니다.
- 원문 좌표·비공백 커버리지·청크 크기·메타데이터·JSON 왕복 검증을 통과했다.
- 짧은 표 7,770개 중 완전히 보존되지 않은 표는 fixed 2,853개, structured 0개다. structured의 1,000자 이하 행 중간 분할도 0개다.
- structured에는 150자 미만 청크 127개가 있으며 섹션 경계 침범은 fixed 2,350개보다 많은 2,579개다. 표 보존 개선만으로 답변 품질 개선을 주장하지 않는다.
- 저장된 질문 벡터로 기존 전체 100문서 인덱스의 검색을 다시 확인했다. 기존 실패 3문항의 근거를 모두 top-5에서 찾은 비율은 fixed/none 3/3, structured/project 0/3이었다. 두 조합의 문서 Recall은 모두 100%여서 문서 단위 Recall만으로 근거 청크 실패를 감지할 수 없다.
- API 호출 0회, 유료 토큰 0개. 준비 스크립트 실행 51.36초이며 검색 성능 비교 시간은 아니다.

## 기존 벡터 재사용 및 제안 범위

동일 임베딩 모델 text-embedding-3-small, 1,536차원, none 모드의 입력 본문이 정확히 같은 경우만 재사용한다.
전체 후보 11,844청크 중 기존 3문서 벡터로 355개 위치(반복 본문 포함), baseline으로 2개 위치를 채울 수 있다.
총 357개 위치를 재사용하고 나머지 11,487개를 새로 임베딩해야 한다.

| 단계 | 신규 기본 요청 | 조건 |
| --- | ---: | --- |
| 후보 structured/none 100문서 | 임베딩 359회 | 누락 입력을 32개씩 모아 요청한 뒤 원래 청크 순서로 복원 |
| smoke 6문항 | 생성 6회 | 질문 벡터 전부 재사용, 기존 성공·근거 위치 퇴행 확인 |
| sample 14문항 | 질문 임베딩 1회 + 생성 14회 | smoke 통과 시 실행; 미캐시 질문 8개를 한 배치로 처리 |
| 합계 | 최대 380회 | SDK 재시도 제외, smoke 실패 시 sample 중단 |

기존 build_index의 원래 32개 청크 묶음마다 누락 입력을 따로 요청하면 빌드 361회가 필요하다.
359회 계획은 실험 실행기에서 누락 벡터를 먼저 준비하고 실제 build_index에 캐시를 재생하는 방식이다.
embedding.py의 배치·기본 설정을 바꾸지 않는다. 캐시 출처·청크 순서·파일 해시를 다시 검사하고 새 경로에만 저장한다.
기존 config에 현재 해시만 붙이지 않고, 빌드에 사용하는 documents.json 바이트 해시를 새 build_index 호출에 전달한다.

토큰은 이전 산정치(3문서 외 본문 8,092,085토큰)를 기준으로 신규 임베딩 약 810만 토큰 이하로 예상한다.
이번에는 추가 캐시 7개 위치를 제외한 토큰을 토크나이저로 다시 세지 않았으므로 정확한 사전 수치나 과금 상한은 아니다.
답변 20개는 이전 평가 사용량을 기준으로 약 10만~13만 토큰을 추가 예상하며 실제 검색 문맥과 모델 출력에 따라 달라진다.
성공 응답 사용량은 기존 Trace/model_call로 집계하고 실패·재시도 과금은 별도로 확인해야 한다.
