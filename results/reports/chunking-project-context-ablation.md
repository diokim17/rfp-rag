# 3문서 청킹·사업명 문맥 분리 실험과 혼합 방식 수정

2026-10-06 UTC. 자동 실험 ID **chy-0008**, 브랜치 `feature/chunking-project-context`.

**이번 3문서에서는 사업명 문맥을 그대로 앞에 붙이는 방식이 근거 검색 퇴행의 주요 요인이었다.** 청킹을 고정해도 문맥을 켜면 실패했고, 문맥을 끄면 두 청킹 전략 모두 목표 3문항의 근거를 찾았다. 본문 벡터 비중을 유지하는 선택형 `project_blend`를 추가하고 저장 벡터만으로 구현을 검증했다.

네 조합의 검색 분리 실험에는 답변 생성이 없다. 이후 별도 승인으로 `structured/none`의 3문서 답변 6개도 검증했다(6절). 3문서 결과를 전체 100문서 성능으로 해석하지 않는다. 기존 100문서 baseline과 `structured/project` 인덱스는 모두 보존했다.

## 1. 근거 위치와 비교 조건

대상은 기존 smoke 6문항의 정답 문서 3개다. 원래 평가 JSON의 질문·정답을 그대로 복사했고, 같은 문서·같은 질문 벡터·같은 모델·top-k=5로 네 조합을 비교했다. 필터는 없다. 기존 인덱스의 해당 문서 벡터만 추출해 `fixed/none`, `structured/project`를 재사용하고, 나머지 두 조합만 새로 임베딩했다.

검색은 기존 `IndexFlatIP`/L2 정규화 방식으로 수행했다. 질문 6개는 한 배치로 임베딩하여 모든 조합에서 재사용했다. 전체 순위도 별도로 계산해 근거가 몇 위로 밀렸는지 확인했다. 평가·검색 모듈은 수정하지 않았다.

실패했던 3문항은 원문에서 직접 확인한 근거 단위를 아래처럼 고정했다. 좌표는 원문 문자 기준 `[start, end)`이다. 각 항목에서 대체 근거 중 하나가 청크에 온전히 포함되면 해당 사실을 찾은 것으로 본다.

| 문항 | 필요한 사실 | 확인한 원문 좌표 |
| --- | --- | --- |
| s02 | 사업기간 | 494–528 또는 1140–1174 |
| s02 | 입찰·계약 방식 | 571–600 또는 3586–3604 |
| s04 | SW 세부예산의 항목명과 금액이 함께 있는 표 행 | 848–894 |
| s05 | 담당 업무를 지정한 표 행 | 76–150 또는 7149–7235 |

단어만 일치하는 경우를 피했다. 예를 들어 같은 기간 표현이 제재 기간에도 나오고, 같은 부서명이 자료 열람 장소에도 나온다. 이런 위치는 정답 근거로 세지 않았다. 근거 본문·문서 ID의 상세 매핑은 Git 제외 경로의 `evidence.json`에 보관한다.

## 2. 네 조합의 검색 결과

각 문항에 필요한 모든 근거가 상위 5개 검색 청크에 포함됐는지를 기준으로 판정한다. s02는 기간과 계약 방식 둘 다 필요하다. 숫자는 전체 청크 순위에서 각 근거가 처음 등장한 순위다.

| 조합 | s02 기간 / 계약 순위 | s04 세부예산 순위 | s05 담당 부서 순위 | 근거를 모두 찾은 문항 |
| --- | ---: | ---: | ---: | ---: |
| fixed / none | 1 / 1 | 1 | 2 | **3 / 3** |
| fixed / project | 9 / 14 | 1 | 48 | **1 / 3** |
| structured / none | 1 / 1 | 1 | 4 | **3 / 3** |
| structured / project | 2 / 18 | 6 | 9 | **0 / 3** |

문서 Recall@5는 네 조합 모두 6문항 평균 100%였다. 따라서 이번처럼 정답 문서 안에서 엉뚱한 청크를 찾는 문제는 문서 Recall만으로 발견하기 어렵다.

보조 지표인 **검색 본문의** 키워드 포함률은 fixed/none 100%, fixed/project 58.33%, structured/none 100%, structured/project 41.67%였다. 이는 답변 키워드 포함률이 아니다. 금액처럼 메타데이터로도 답할 수 있는 항목에서는 본문 키워드와 답변의 성공 여부가 다를 수 있다.

청킹을 고정한 비교에서도 `project`의 퇴행이 나타나 문맥 추가 자체의 영향을 확인했다. 다만 청킹과 문맥의 상호작용도 있고, 3문서로 검색 경쟁을 줄인 진단이므로 전체 데이터에서의 영향 크기는 미확인이다.

## 3. embedding.py 수정과 추가 비용 없는 검증

`RFP_EMBEDDING_CONTEXT=project_blend`를 선택형으로 추가했다. 기본값 `none`과 기존 `project`의 동작은 그대로다.

```text
body = normalize(embed(원문 청크))
contextual = normalize(embed(사업명·기관명 + 원문 청크))
document_vector = normalize(0.8 * body + 0.2 * contextual)
```

- 문서 벡터에만 적용한다. 질문 임베딩과 검색·생성 코드는 변경하지 않았다.
- 메타데이터가 비어 문맥 입력과 본문이 같으면 두 번째 임베딩을 생략한다.
- 본문·문맥 벡터 차원이 다르면 저장 전에 실패한다. 기존 인덱스 보존과 벡터/청크 순서를 유지한다.
- `Chunk.text`, 메타데이터, 문자 위치, 공개 함수 시그니처, 반환 형식과 필수 키를 유지했다.
- 기존 선택 키 `embedding_context=project_blend`, `embedding_context_version=1`로 식별한다. 추가 config 키나 CLI 옵션, 의존성은 도입하지 않았다. 0.2는 이 모드 v1의 고정 비중이며 바꾸면 버전도 바꿔야 한다.
- 기존 Langfuse `model_call` 경로를 사용하므로 두 요청의 토큰을 모두 집계한다. 사업명·기관명·본문은 추적 기록에 추가하지 않는다.

이미 확보한 두 종류의 벡터를 사용해 문맥 비중 0.1/0.2/0.3/0.5를 오프라인으로 비교했다. 두 청킹 전략 모두 이 네 비중에서 3문항의 근거를 찾았다. 0.2를 보수적 고정값으로 선택했으며 최적 비중이라고 주장하지 않는다. 같은 진단 문항에서 탐색했으므로 독립 검증도 필요하다.

수정한 실제 `build_index` 경로에도 저장 벡터를 재생하여 별도 인덱스를 생성하고 로드·검색했다. 네트워크 임베딩 함수만 캐시 응답으로 대체했으며 청킹·혼합·저장·로드 코드는 실제 구현을 실행했다.

| 혼합 후보(문맥 비중 0.2) | s02 기간 / 계약 순위 | s04 순위 | s05 순위 | 근거 확보 |
| --- | ---: | ---: | ---: | ---: |
| fixed / project_blend | 1 / 1 | 1 | 2 | 3 / 3 |
| structured / project_blend | 1 / 1 | 2 | 4 | 3 / 3 |

혼합 후보 역시 질문 6개의 검색 본문 키워드 포함률은 100%였다. 다만 `none`보다 더 좋은 결과를 보인 것은 아니므로 현재 데이터에서 혼합 비용의 이득은 입증되지 않았다. 다음 유료 검증의 우선 후보는 비용이 더 적고 표 보존도 유지하는 **structured/none**이다. project_blend는 문맥을 제한적으로 유지하는 후속 비교 후보로 남긴다.

캐시가 없는 새 build에서 project_blend는 문맥이 있는 청크를 두 번 임베딩한다. 본문용 비용과 문맥 포함 입력 비용을 합산해야 한다. 이번 혼합 탐색과 구현 검증에서는 기존 벡터를 재사용해 **추가 API 호출 0회**였다.
