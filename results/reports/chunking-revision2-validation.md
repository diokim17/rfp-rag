# structured/none v2 최종 회귀 검증

후속 변경 안내: 이 보고서는 아래 코드 해시의 **섹션·표 메타데이터 추가 전** 평가 기록입니다. 이후 변경과 오프라인 검증은 [섹션·표 메타데이터 검증](section-table-metadata-validation.md)을 참고하세요. 아래 기존 인덱스에는 새 메타데이터가 없고, 코드 해시를 검사하는 과거 실험 실행기는 현재 코드로 재실행할 수 없습니다. 기존 답변 점수를 새 메타데이터가 포함된 생성 입력의 평가로 해석하지 않습니다.

2026-10-06 UTC. 사용자가 변경 청크 임베딩·전체 검색 퇴행 확인·영향 답변 재검증을 승인해 실행했다.

**결론: 목차 경계 수정으로 f01의 기간·예산 근거와 답변이 회복됐고, 이번 14문항에서 새 퇴행을 발견하지 않았다.**
이는 현재 100문서·평가셋 범위의 확인이며, 모든 기관별 목록 검색이나 사업명 문맥 임베딩의 개선을 입증한 것은 아니다.
f08의 기존 목록 누락은 검색 담당자와 협의할 과제로 남는다. 기본 fixed/none은 바꾸지 않았다.

## 변경과 계약

- 첫 청크 후반의 첫 섹션 앞에 독립된 목차 제목이 있으면 섹션 직전 대신 문단 경계를 사용한다.
- 표 보존·크기 제한·원문 좌표와 사업명 등 메타데이터는 유지한다. 문서 ID나 특정 사업명을 조건으로 사용하지 않는다.
- 실제 100문서에서 1문서의 2청크만 바뀌며, 전체 11,844청크 중 11,842개는 기존 none 임베딩을 재사용했다.
- structured의 `chunking_version=2`로 구분한다. fixed/boundary는 버전 1과 기존 출력이 동일하다.
- 공개 함수·인자·기본값, Document → Chunk → Hit → Answer, config 필수 키와 documents_sha256 저장 계약을 유지한다.
- 100문서의 사업명이 모든 청크에 원래 값으로 전달되고, 저장 본문이 원문의 정확한 슬라이스임을 확인했다.
  CSV 사업명 자체가 올바른지 의미적으로 전수 검토하거나 빈 사업명을 추론하는 기능은 포함하지 않는다.

## 검증 순서와 실제 결과

1. 문서·평가셋·기존 인덱스·질문 벡터·코드 해시를 확인했다. 새 실행기는 임시 폴더와 가짜 2입력 응답으로 저장 순서 및 14문항 검색 비교를 먼저 검증했다.
2. 변경 본문 2개(합계 1,290자)를 한 배치로 임베딩하고 기존 벡터와 원래 순서로 결합했다. 실제 build_index를 캐시 재생으로 실행해 새 v2 인덱스를 생성했다.
3. 14문항 모두 기존 질문 벡터로 실제 retrieve를 실행했다. 이전 sample 결과와 비교할 때 자료가 바뀐 문항은 s01·f01·f02·f03이었다.
4. 나머지 10문항은 생성에 전달되는 sources가 본문·메타데이터·citation·순서·점수까지 정확히 같았다. 이 10문항의 답변은 재생성하지 않았다.
5. 영향 문항 4개만 실제 generate_answer/evaluate로 재평가했고 Recall@5·키워드 포함률 모두 100%였다. 네 답변과 인용 근거를 로컬에서 직접 확인했다.

f01의 기간·예산을 담은 첫 청크 [0,789)가 검색 1위가 됐고, 답변이 두 값을 근거와 함께 제시했다.
v1은 목차에서 분리된 근거 청크가 28위였으며 기간을 확인하지 못했다. 나머지 세 재평가 문항도 기존 성공을 유지했다.

| 비교 | 문서 Recall@5 | 답변 키워드 포함률 | 답변 측정 방식 |
| --- | ---: | ---: | --- |
| baseline fixed/none | 94.0476% | 94.0476% | 이전 14문항 실제 생성 |
| structured/none v1 | 96.4286% | 92.8571% | 이전 14문항 실제 생성 |
| structured/none v2 | 96.4286% | 96.4286% | 검색은 14문항 재실행, 답변은 영향 4개 새 생성 + 입력 동일 10개 기존 결과 재사용 |

**v2의 96.43%를 14개 답변 전체를 새로 생성한 독립 평가로 해석하면 안 된다.**
질문·생성 설정·검색 자료가 그대로인 10개 응답을 포함한 회귀 집계다. 생성 변동성이나 새로운 질문으로의 일반화는 측정하지 않았다.
새로 생성한 4개 답변의 평균 시간은 2.7409초이나, 질문 구성이 다른 전체 baseline과 속도 비교하지 않는다.

## 테스트와 보존 확인

- 현재 embedding.py 코드 해시는 `ded099c39429fb6d5cec49ecf766ffac6d52c9a496d2558fa1b4a9757dbe2c85`이며 앞서 **79개 unittest가 통과한 코드와 동일**하다.
- 목차 표기·LF/CRLF·인라인 오탐·표 경계·크기·큰 overlap·일반 섹션·버전 저장을 포함한 회귀 테스트가 있다. 합성 사례는 v1 실패와 v2 성공을 재현한다.
- 100문서 전체 원문 커버리지·사업명 연결·표 보존·고정/문단 전략 동일성을 오프라인으로 검증했다. 짧은 표 7,770개 보존과 1,000자 이하 행 중간 분할 0개를 유지한다.
- 새 v2 인덱스의 벡터 전체 순서, 청크 JSON, config와 문서 SHA-256을 대조했다. baseline·이전 project 후보·v1 인덱스 해시는 그대로다.

- 이 평가 당시 코드 수정과 보고서는 로컬 미커밋 상태였다. 평가 단계에서 PR #5에 추가 푸시하거나 병합하지 않았다.

## 남은 한계와 인계

f08은 2개 사업 중 1개만 검색되는 기존 실패다. 사업명은 청크 metadata에 있지만 다른 문서가 top-5를 차지한다.
기존 기관 필터를 적용한 오프라인 진단에서는 두 인덱스 모두 2개를 찾았다.
질문에서 기관 필터를 적용하거나 목록 질의의 문서 다양성을 다루는 변경은 검색·통합 담당자와 협의해야 한다.
이번에 평가셋·공식 필터·검색 모듈을 바꿔 점수를 보정하지 않았다.

사업명·기관명을 임베딩 입력에 추가하는 project/project_blend는 별도 실험 옵션이며 기본 적용하지 않는다.
이번에 검증한 조합은 **structured/none v2**다. 표 구조 보존과 해당 평가셋 결과를 근거로 선택 사용 가능하지만 전면 기본 전환은 하지 않았다.

## 사용 및 재현

새 인덱스는 이미 생성돼 있어 다시 임베딩할 필요가 없다. parse도 재실행할 필요가 없다.

```bash
.venv/bin/python run.py ask \
  --processed-dir data/processed/chunking-followup-20261006T070744037625Z \
  --index-dir indexes/chunking-followup-20261006T070744037625Z/structured_none_v2 \
  --results-dir results/chunking-followup-20261006T070744037625Z/revision2/ask \
  --question '검증할 질문'
```

위 질의 명령은 유료 호출을 발생시킨다. 문서가 달라지면 새 build가 필요하며 config의 해시만 바꿔 우회하지 않는다.

오프라인 재확인:

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python results/chunking-followup-20261006T070744037625Z/run_revision2.py check
.venv/bin/python results/chunking-followup-20261006T070744037625Z/run_revision2.py compare
```

상세 원문 결과·캐시·입력 동일성 비교는 `results/chunking-followup-20261006T070744037625Z/revision2/`에 Git 제외 상태로 보관한다.
